## Why this matters
Real decisions are rarely one `if`. A thermostat has to weigh safety, an on/off switch, who is home, and how far the room is from the target, and the answer depends on which rule is checked first. Writing the rules as an ordered list of guard clauses keeps the code flat, testable, and safe.

## What you will build
A `thermostat(temp, target, mode="auto", home=True)` function that returns `ALERT: check sensor`, `OFF`, `COOLING`, `HEATING`, or `IDLE`. You build it one rule at a time, extend it with a time-of-day target, test every branch with `assert`, and finish with the complete example program from the cheat sheet.

## Before you start
Use Python 3.10 or newer and create each named file in a practice folder. Every example is independent. Run each file with `python3 filename.py` on macOS/Linux or `py -3 filename.py` in Windows PowerShell.

You should be comfortable with `if`/`elif`/`else` and comparison operators from the earlier conditionals lessons. The rules are checked from top to bottom, and the first rule that matches decides the result:

| # | Rule | Result |
| --- | --- | --- |
| 1 | Safety: `temp >= 40` or `temp <= 5` | `ALERT` |
| 2 | Mode is `"off"` | `OFF` |
| 3 | Comfort band: 1 degree at home, 4 when away | (sets `band`) |
| 4 | Too hot and mode is `auto` or `cool` | `COOLING` |
| 5 | Too cold and mode is `auto` or `heat` | `HEATING` |
| 6 | Anything else | `IDLE` |

## Step 1: Rule 1, a safety guard clause
A guard clause is an `if` that returns immediately, so the rest of the function never runs for that case. Rule 1 combines two tests with `or`: the reading is unsafe when it is too hot or too cold. The same range can be written with a chained comparison as `5 < temp < 40`.

```python title="safety_guard.py" file
def safety_check(temp):
    if temp >= 40 or temp <= 5:
        return "ALERT: check sensor"
    return "ok"


for reading in [45, 40, 22, 6, 5, -3]:
    print(reading, safety_check(reading), 5 < reading < 40)
```


Both limits are inclusive, so exactly `40` and exactly `5` raise the alert. The chained comparison is `True` only where the check returns `ok`.

## Step 2: Order is priority
Rules are tested in the order they are written, so the order is the priority. Safety must come before the `"off"` test. Here the same two rules are written in both orders and run on four readings, including a frozen room at 3 degrees with the system switched off.

```python title="priority_order.py" file
def off_first(temp, mode):
    if mode == "off":
        return "OFF"
    if temp >= 40 or temp <= 5:
        return "ALERT: check sensor"
    return "IDLE"


def safety_first(temp, mode):
    if temp >= 40 or temp <= 5:
        return "ALERT: check sensor"
    if mode == "off":
        return "OFF"
    return "IDLE"


for temp, mode in [(3, "off"), (45, "off"), (20, "off"), (20, "auto")]:
    print(temp, mode, "| off first:", off_first(temp, mode), "| safety first:", safety_first(temp, mode))
```

**Watch out:** if the `OFF` test came first, a frozen pipe or an overheating room would never raise an alert while the system is off. The two versions only differ when both rules match.

## Step 3: Rule 3, default arguments and a ternary band
Default arguments make the common call short: `mode="auto"` and `home=True` apply unless the caller says otherwise. The comfort band is picked with a ternary expression, `1 if home else 4`, which is an `if`/`else` that produces a value. Pass `home=False` by keyword so it cannot be mistaken for another parameter.

```python title="band_and_defaults.py" file
def comfort_band(home=True):
    return 1 if home else 4


def describe(temp, target, mode="auto", home=True):
    band = comfort_band(home)
    diff = temp - target
    return f"mode={mode} home={home} band={band} diff={diff}"


print(comfort_band(), comfort_band(True), comfort_band(home=False))
print(describe(26, 22))
print(describe(26, 22, "heat"))
print(describe(26, 22, home=False))
print(describe(22.5, 22))
print(describe(26, 22, False))
```

## Step 4: Rules 4 to 6, membership and a negative threshold
The room is too hot when `diff > band` and too cold when `diff < -band`. The unary minus turns the band into a negative threshold. Membership with `in` checks which modes may act: `mode in ("auto", "cool")`. Anything that matches neither rule falls through to `IDLE`.

```python title="pick_action.py" file
def pick_action(diff, band, mode):
    if diff > band and mode in ("auto", "cool"):
        return "COOLING"
    elif diff < -band and mode in ("auto", "heat"):
        return "HEATING"
    return "IDLE"


for mode in ["auto", "cool", "heat", "off"]:
    print(f"{mode:5} hot: {pick_action(4, 1, mode):8} cold: {pick_action(-4, 1, mode)}")

band = 1
print("-band is", -band)
print(pick_action(1, 1, "auto"), pick_action(-1, 1, "auto"))

mode = "heat"

print(mode in ("auto", "cool"))
```

## Step 5: Put the rules together
Now the six rules form one function. The guard clauses come first and return early, so there is no deep nesting, and the three comments mark the rule numbers. The eight calls from the sheet cover every result, including a heat-only mode, an away band, a sensor fault, and the off switch.

```python title="thermostat.py" file
def thermostat(temp, target, mode="auto", home=True):
    # 1. safety wins over everything
    if temp >= 40 or temp <= 5:
        return "ALERT: check sensor"
    # 2. system switched off
    if mode == "off":
        return "OFF"
    # 3. wider comfort band when nobody is home
    band = 1 if home else 4
    diff = temp - target
    # 4-6. pick the action
    if diff > band and mode in ("auto", "cool"):
        return "COOLING"
    elif diff < -band and mode in ("auto", "heat"):
        return "HEATING"
    return "IDLE"


print(thermostat(30, 22))                # hot
print(thermostat(18, 22))                # cold
print(thermostat(22.5, 22))              # within band
print(thermostat(26, 22, "heat"))        # hot, heat-only
print(thermostat(26, 22, home=False))    # away: wide band
print(thermostat(30, 22, home=False))    # far outside
print(thermostat(45, 22))                # sensor fault
print(thermostat(20, 22, "off"))         # switched off
```

## Step 6: Extend it with a target by time of day
Instead of a fixed target, a second function chooses one from the hour and whether anyone is home. The `not home` guard comes first. Chained comparisons such as `6 <= hour < 9` and combined tests with `or` describe the morning, the evening, and the night; everything left is daytime.

```python title="target_for.py" file
def target_for(hour, home):
    if not home:
        return 17
    if 6 <= hour < 9 or 17 <= hour < 23:
        return 22                  # morning, evening
    if hour >= 23 or hour < 6:
        return 19                  # night
    return 20                      # daytime


print(target_for(7, True), target_for(2, True), target_for(13, False))

for hour in [0, 5, 6, 8, 9, 12, 16, 17, 22, 23]:
    print(f"{hour:02}:00 ->", target_for(hour, True))
```

## Step 7: Test every branch with assert
`assert condition` does nothing when the condition is true and raises `AssertionError` when it is false, so each branch can be tested in one line. A second argument becomes the error message. Assertions are skipped when Python runs with the `-O` option, so use them for quick checks, not for validating user input.

```python title="thermostat_tests.py" file
def thermostat(temp, target, mode="auto", home=True):
    if temp >= 40 or temp <= 5:
        return "ALERT: check sensor"
    if mode == "off":
        return "OFF"
    band = 1 if home else 4
    diff = temp - target
    if diff > band and mode in ("auto", "cool"):
        return "COOLING"
    elif diff < -band and mode in ("auto", "heat"):
        return "HEATING"
    return "IDLE"


assert thermostat(30, 22) == "COOLING"
assert thermostat(18, 22) == "HEATING"
assert thermostat(22.5, 22) == "IDLE"
assert thermostat(45, 22, "off").startswith("ALERT")
assert thermostat(20, 22, "off") == "OFF"
assert thermostat(26, 22, "heat") == "IDLE"
assert thermostat(26, 22, home=False) == "IDLE"
assert thermostat(30, 22, home=False) == "COOLING"
print("all tests passed")

try:
    assert thermostat(30, 22) == "HEATING", "expected HEATING for a hot room"
except AssertionError as error:
    print("AssertionError:", error)
```

## Step 8: Name the magic numbers and return a dict
Numbers such as `40`, `5`, `1`, and `4` are magic numbers. Naming them as constants puts each rule threshold in one place. When the caller needs more than a word, return a dict such as `{"action": "COOLING", "fan": "high"}`. The fan rule here is a teaching choice: `high` when the gap is 8 degrees or more, otherwise `low`.

```python title="constants_and_dict.py" file
MAX_SAFE = 40
MIN_SAFE = 5
BAND_HOME = 1
BAND_AWAY = 4


def thermostat(temp, target, mode="auto", home=True):
    if temp >= MAX_SAFE or temp <= MIN_SAFE:
        return {"action": "ALERT", "fan": "off"}
    if mode == "off":
        return {"action": "OFF", "fan": "off"}
    band = BAND_HOME if home else BAND_AWAY
    diff = temp - target
    fan = "high" if abs(diff) >= 8 else "low"
    if diff > band and mode in ("auto", "cool"):
        return {"action": "COOLING", "fan": fan}
    elif diff < -band and mode in ("auto", "heat"):
        return {"action": "HEATING", "fan": fan}
    return {"action": "IDLE", "fan": "off"}


print(thermostat(30, 22))
print(thermostat(26, 22))
print(thermostat(22.5, 22))
print(thermostat(45, 22))

result = thermostat(14, 22)
print(result["action"], result["fan"])

print(thermostat(36, 22)["action"])
MAX_SAFE = 35
print(thermostat(36, 22)["action"])
```

## Step 9: Avoid rapid cycling with hysteresis
Near the band edge, a plain rule flips on and off with every small reading change. Hysteresis fixes this: switch cooling on above target plus band, but switch it off only when the room reaches the target. The controller remembers its state, so between those two points it keeps doing what it was doing.

```python title="hysteresis.py" file
BAND = 1


def plain_cooling(temp, target):
    return temp - target > BAND


class CoolingController:
    def __init__(self, target):
        self.target = target
        self.on = False

    def update(self, temp):
        diff = temp - self.target
        if diff > BAND:
            self.on = True
        elif diff <= 0:
            self.on = False
        return self.on


def switches(states):
    return sum(1 for a, b in zip(states, states[1:]) if a != b)


readings = [23.1, 22.9, 23.1, 22.9, 22.4, 21.9, 22.3]
controller = CoolingController(22)
plain_states = []
smart_states = []

for temp in readings:
    plain = plain_cooling(temp, 22)
    smart = controller.update(temp)
    plain_states.append(plain)
    smart_states.append(smart)
    print(f"{temp}: plain={'ON' if plain else 'off'} hysteresis={'ON' if smart else 'off'}")

print("switches: plain", switches(plain_states), "hysteresis", switches(smart_states))
```

## How it works
Python evaluates an `if`/`elif` chain from top to bottom and runs the first branch whose condition is true. A `return` inside a guard clause ends the function at once, which is why the safety rule written first beats every later rule and why the function stays flat instead of nesting. The decision flow looks like this:

```text title="Decision flow"
temp out of safe range?   --yes--> ALERT
        | no
mode is "off"?            --yes--> OFF
        | no
band = 1 (home) or 4 (away)
        |
too hot and auto/cool?    --yes--> COOLING
        | no
too cold and auto/heat?   --yes--> HEATING
        | no
      IDLE
```

`or` and `and` short-circuit and return one of their operands, which is why `mode == "auto" or "cool"` is always truthy. `in` tests membership in a tuple of allowed modes, and `diff < -band` uses a negative threshold for the cold side. Default arguments let callers omit `mode` and `home`. Further extensions fit the same shape: a humidity branch, or `match mode:` once each mode has its own behaviour.

## Common errors
### `mode == "auto" or "cool"` is always true
The string `"cool"` is truthy on its own, so the condition never checks the mode. Write `mode in ("auto", "cool")` or `mode == "auto" or mode == "cool"`.

### The alert never fires while the system is off
The `"off"` test was written before the safety test, so it returns first. Put the safety guard at the top and keep the most important rule first.

### `thermostat(26, 22, False)` treats `False` as the mode
Positional arguments fill parameters left to right, so `False` lands in `mode`. Pass it by keyword: `thermostat(26, 22, home=False)`.

### Answering `Y` counts as "not at home"
`input(...) == "y"` is case-sensitive, so `"Y"` gives `False`. Normalise first with `.lower()` before comparing.

### `ValueError: could not convert string to float: 'abc'`
`float()` cannot convert text that is not a number. Check the answer or catch `ValueError` before calling `thermostat`.

### `SyntaxError: invalid syntax` on `if mode = "off":`
A single `=` assigns; comparing needs `==`. Write `if mode == "off":`.

## Recap
- Rules are checked top to bottom, so the order is the priority: write the safety guard clause first and return early.
- Use `or`/`and` for combined tests, `in` for membership, a ternary for the band, `-band` for the cold threshold, and default arguments for common calls.
- Test every branch with `assert`, name the magic numbers, and return a dict when callers need more than a string.
