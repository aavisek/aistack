## Why this matters
An application becomes easier to change when responsibilities are separated. Modeling entities, services, and policies as focused objects prevents one large class from owning every rule.

## What you will build
A small library checkout application with books, members, a catalog, and a checkout service.

## Before you start
Create `library.py`. This lesson uses only the standard library and runs with Python 3.10 or newer.

## Step 1: Model the entities
Start with objects that own their own data and small state transitions.

```python title="library.py" file
class Book:
    def __init__(self, title):
        self.title = title
        self.checked_out = False


class Member:
    def __init__(self, name):
        self.name = name
        self.borrowed = []
```

## Step 2: Add a focused catalog
The catalog owns book lookup rather than making every caller search a list.

```python title="catalog.py" file
class Catalog:
    def __init__(self, books):
        self._books = {book.title: book for book in books}

    def find(self, title):
        return self._books.get(title)
```

## Step 3: Put the use case in a service
The service coordinates objects and enforces the checkout rules.

```python title="checkout.py" file
class CheckoutService:
    def checkout(self, member, catalog, title):
        book = catalog.find(title)
        if book is None:
            return "book not found"
        if book.checked_out:
            return "book unavailable"
        book.checked_out = True
        member.borrowed.append(book)
        return f"{member.name} borrowed {book.title}"
```

## Step 4: Compose and run the application
Composition wires the objects together at the application boundary.

```python title="library.py" file
class Book:
    def __init__(self, title):
        self.title = title
        self.checked_out = False


class Member:
    def __init__(self, name):
        self.name = name
        self.borrowed = []


class Catalog:
    def __init__(self, books):
        self._books = {book.title: book for book in books}

    def find(self, title):
        return self._books.get(title)


class CheckoutService:
    def checkout(self, member, catalog, title):
        book = catalog.find(title)
        if book is None:
            return "book not found"
        if book.checked_out:
            return "book unavailable"
        book.checked_out = True
        member.borrowed.append(book)
        return f"{member.name} borrowed {book.title}"


book = Book("Python Design")
catalog = Catalog([book])
member = Member("Mina")
service = CheckoutService()
print(service.checkout(member, catalog, "Python Design"))
print(service.checkout(member, catalog, "Python Design"))
print(service.checkout(member, catalog, "Missing"))
```

```bash title="Terminal" verify="run"
python3 library.py
```

```text title="Expected output"
Mina borrowed Python Design
book unavailable
book not found
```

## Step 5: Design for change
The service depends on the catalog's `find` behavior, not on its private dictionary. That boundary makes it possible to replace the catalog with a database-backed implementation later.

```python title="fake_catalog.py" file
class FakeCatalog:
    def __init__(self, book):
        self.book = book

    def find(self, title):
        return self.book if title == self.book.title else None


class Book:
    def __init__(self, title):
        self.title = title
        self.checked_out = False


book = Book("Practice")
catalog = FakeCatalog(book)
print(catalog.find("Practice").title)
```

```bash title="Terminal" verify="run"
python3 fake_catalog.py
```

```text title="Expected output"
Practice
```

## How it works
The entities hold domain state, the catalog encapsulates lookup, and the service coordinates a use case. Composition assembles these roles. Small boundaries make each part testable and allow implementation changes without rewriting callers.

## Verify against the requirements
- [x] Domain entities own their state → Step 1
- [x] Lookup is isolated behind a catalog → Step 2
- [x] A service coordinates and validates a use case → Step 3
- [x] A fake implementation can replace a dependency → Step 5

## Common errors
### Creating one “god object”
Split responsibilities when a class has unrelated reasons to change.

### Exposing every internal collection
Expose operations such as `find()` instead of making callers depend on private storage.

### Mixing input/output with domain rules
Keep terminal or web concerns at the application boundary.

## Recap
- Model stateful entities with focused responsibilities.
- Use services to coordinate use cases and rules.
- Compose dependencies at the application boundary.
