## Why this matters
Clients can send missing, malformed, or unexpected data. A predictable API checks input at its boundary and returns useful errors without exposing implementation details.

## Step 1: Define strict input schemas
`strict()` rejects keys the API did not define. A create requires a title and year; a patch allows a subset but refuses an empty update.

```ts title="src/validation.ts" file
import { z } from "zod";

const currentYear = new Date().getFullYear();
const bookFields = {
  title: z.string().trim().min(1).max(100),
  author: z.string().trim().min(1).max(100),
  year: z.number().int().min(0).max(currentYear)
};

export const createBookSchema = z.object(bookFields).strict();
export const replaceBookSchema = createBookSchema;
export const patchBookSchema = z.object(bookFields).partial().strict()
  .refine((value) => Object.keys(value).length > 0, "At least one field is required");
export type CreateBookInput = z.infer<typeof createBookSchema>;
```

## Step 2: Create predictable application errors
Expected failures carry a status and code. Validation details include field paths; unexpected errors are reported to the server log but do not leak stack traces to production clients.

```ts title="src/errors.ts" file
import type { ErrorRequestHandler, NextFunction, Request, RequestHandler, Response } from "express";
import { ZodError, type ZodType } from "zod";

export class AppError extends Error {
  constructor(
    message: string,
    public readonly status: number,
    public readonly code: string
  ) {
    super(message);
  }
}

export class NotFoundError extends AppError {
  constructor(message = "Resource not found") {
    super(message, 404, "NOT_FOUND");
  }
}

export class ValidationError extends AppError {
  constructor(message: string, public readonly details?: unknown) {
    super(message, 400, "VALIDATION_ERROR");
  }
}

type AsyncRoute = (req: Request, res: Response, next: NextFunction) => unknown;

export function asyncHandler(handler: AsyncRoute): RequestHandler {
  return (req, res, next) => {
    Promise.resolve(handler(req, res, next)).catch(next);
  };
}

export function validateBody(schema: ZodType): RequestHandler {
  return (req, _res, next) => {
    const result = schema.safeParse(req.body);
    if (!result.success) {
      const details = result.error.issues.map((issue) => ({
        field: issue.path.join("."),
        message: issue.message
      }));
      return next(new ValidationError("Request body is invalid", details));
    }
    req.body = result.data;
    next();
  };
}

export const errorHandler: ErrorRequestHandler = (error, _req, res, _next) => {
  let status = 500;
  let code = "INTERNAL_ERROR";
  let message = "An unexpected error occurred";
  let details: unknown;

  if (error instanceof AppError) {
    status = error.status;
    code = error.code;
    message = error.message;
    if (error instanceof ValidationError) details = error.details;
  } else if (error instanceof ZodError) {
    status = 400;
    code = "VALIDATION_ERROR";
    message = "Request body is invalid";
    details = error.issues;
  } else if (error instanceof SyntaxError && "body" in error) {
    status = 400;
    code = "INVALID_JSON";
    message = "Request body must be valid JSON";
  } else {
    console.error(error);
  }

  res.status(status).json({
    error: {
      code,
      message,
      ...(details === undefined ? {} : { details }),
      ...(process.env.NODE_ENV === "production" || error instanceof AppError
        ? {}
        : { debug: error instanceof Error ? error.message : "Unknown error" })
    }
  });
};
```

## Step 3: Wire security middleware and route validation
Middleware order matters: add security headers and explicit-origin CORS before bounded JSON parsing, then route. Put the error handler last so it receives failures from parsing and routes.

```ts title="src/app.ts integration example"
import express from "express";
import cors from "cors";
import helmet from "helmet";
import { asyncHandler, errorHandler, NotFoundError, validateBody } from "./errors.js";
import { createBookSchema, patchBookSchema } from "./validation.js";
import { booksService } from "./books.service.js";

export const app = express();
app.use(helmet());
app.use(cors({ origin: process.env.WEB_ORIGIN ?? "http://localhost:3000" }));
app.use(express.json({ limit: "100kb" }));

app.post("/books", validateBody(createBookSchema), asyncHandler(async (req, res) => {
  const book = booksService.create(req.body);
  res.location(`/books/${book.id}`).status(201).json(book);
}));

app.patch("/books/:id", validateBody(patchBookSchema), asyncHandler(async (req, res) => {
  const id = Number(req.params.id);
  const book = booksService.patch(id, req.body);
  if (!book) throw new NotFoundError("Book not found");
  res.json(book);
}));

app.use((_req, _res, next) => next(new NotFoundError("Route not found")));
app.use(errorHandler);
```

Apply `validateBody(replaceBookSchema)` to PUT and `asyncHandler` to every async route. The same patterns apply to GET and DELETE error paths.

## Step 5: Test boundary and unexpected errors
Add tests alongside the FD-06 endpoint tests. Verify individual bad fields, unknown keys, malformed JSON, and a deliberately thrown async error; follow it with a healthy request to prove the app remains up.

```ts title="tests/errors.test.ts" file
import test from "node:test";
import assert from "node:assert/strict";
import express from "express";
import request from "supertest";
import { app } from "../src/app.js";
import { asyncHandler, errorHandler } from "../src/errors.js";

test("invalid book fields and unknown keys use the error shape", async () => {
  for (const body of [
    { title: "", author: "A. Writer", year: 2000 },
    { title: "Book", author: "A. Writer", year: new Date().getFullYear() + 1 },
    { title: "Book", author: "A. Writer", year: 2000, surprise: true }
  ]) {
    const response = await request(app).post("/books").send(body);
    assert.equal(response.status, 400);
    assert.equal(typeof response.body.error.code, "string");
    assert.equal(typeof response.body.error.message, "string");
  }
});

test("malformed JSON and missing records are client errors", async () => {
  const malformed = await request(app).post("/books")
    .set("content-type", "application/json").send("{");
  assert.equal(malformed.status, 400);
  assert.ok(malformed.body.error.code);
  const missing = await request(app).get("/books/9999");
  assert.equal(missing.status, 404);
  assert.equal(missing.body.error.code, "NOT_FOUND");
});

test("an unexpected async failure is handled and the app stays available", async () => {
  const testApp = express();
  testApp.get("/boom", asyncHandler(async () => {
    throw new Error("unexpected failure");
  }));
  testApp.get("/healthy", (_req, res) => res.json({ status: "ok" }));
  testApp.use(errorHandler);

  const failure = await request(testApp).get("/boom");
  assert.equal(failure.status, 500);
  assert.equal(failure.body.error.code, "INTERNAL_ERROR");
  assert.equal(typeof failure.body.error.message, "string");
  assert.equal((await request(testApp).get("/healthy")).status, 200);
});
```

## How it works
Validation turns untrusted JSON into a known shape before business logic sees it. `next(error)` skips normal middleware and reaches the final error handler. A single serializer makes failures predictable; production mode suppresses debug details.

## Verify against the requirements
- [ ] Title is 1–100 characters, year is an integer from 0 through the current year, and unknown keys fail → Steps 1 and 5.
- [ ] Not-found, validation, malformed JSON, and unexpected failures use the shared error envelope → Steps 2–5.
- [ ] Async rejections reach the final handler through the wrapper → Step 2.
- [ ] Helmet, explicit-origin CORS, and a 100 KiB JSON body limit are configured → Step 3.
- [ ] Production error responses do not expose stack traces; invalid input does not stop later requests → Steps 2, 4, and 5.

## Common errors
### The error handler never runs
Register it after parsers, routes, and the 404 middleware.
### Unknown fields are silently accepted
Use Zod's `.strict()` schema rather than relying on TypeScript types at runtime.
### A rejected async route is unhandled
Wrap it and forward the rejection to `next`.

## Recap
- Validate unknown client data at the HTTP boundary with a runtime schema.
- Forward failures to one error handler with a stable response shape.
- Limit request bodies, configure security middleware, and hide internal details in production.
